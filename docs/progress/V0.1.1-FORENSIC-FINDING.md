POLARIS V0.1.1 — STEP 1 FORENSIC FINDING
=======================================

Reproduced against the *stored documents* of the two records that reached the
public API in the V0.1 milestone. No code edited yet.

--------------------------------------------------------------------
Observed bypass
--------------------------------------------------------------------
There are TWO, not one. Both end at the same place: the record is extracted,
created in `pending_review`, approved through `ReviewService.approve`, and
published because the quality gate has no check that the source page is an
opportunity page.

Production path:

  AcquisitionService.acquire_from_source
    -> connector.fetch(url)                      # raw document stored
    -> self._page_intent(raw_doc)                # classify_page_intent
    -> if intent not in (DETAIL, UNKNOWN): skip  # <-- the only page-level gate
    -> run_pipeline(document_id, ...)            # creates Scholarship
    -> _persist_with_dedup -> record_submission  # extraction_status = pending_review
    -> ReviewService.approve                     # quality gate
    -> published_filter() == 'approved'          # public API

--------------------------------------------------------------------
BYPASS #2 — aggregator listing page classified as DETAIL
--------------------------------------------------------------------
URL:   https://www.wemakescholars.com/post-doc-scholarships-for-international-students
Result: classify_page_intent -> SCHOLARSHIP_DETAIL / 0.75   (is_detail = True)
Evidence produced by the classifier:
  title      = '190+ Post Doc scholarships 2026-27 [Updated]'
  programme_links = 78
  headings   = ['190+ Post Doc Scholarships, grants, fellowships for International
                 Students to study abroad',
                 'PM Yasasvi Post-Matric Scholarship for OBC Students - DNHDD 2026',
                 'Canadian National Graduate Scholarship 2026',
                 'The Smithsonian Institution Fellowship Program 2027',
                 'NSERC - Postdoctoral Fellowship Program 2026', ... ]

Why the existing page intent does not stop it — every collection rule misses,
in order:

  rule 5  (collection by path)  `/post-doc-scholarships-for-international-students`
                                is not a bare collection segment
  rule 6  (index shape)         requires `programme_links >= 5 AND
                                (category_hits OR not title_funding)`.
                                programme_links=78 passes, BUT title_funding is
                                True and `_CATEGORY_LANGUAGE` does not match
                                "190+ Post Doc scholarships" (the vocabulary
                                holds "postgraduate scholarships",
                                "phd scholarships", ... — not "post doc").
                                category_hits = []  => rule does not fire.
  rule 6b (title declares one)  `_OVERVIEW_TITLE` matches "list of", "all
                                scholarships", "types of", "an overview" —
                                none present in "190+ Post Doc scholarships
                                2026-27"  => does not fire.
  rule 7  (detail)              FIRES. title_funding=True; detail_points=2
                                (deadline + eligibility language both appear
                                in the listing's boilerplate); claim_points=2
                                (title_funding + not collection_last).
                                => SCHOLARSHIP_DETAIL.

So the classifier reaches the detail rule because the page states deadline and
eligibility *wording* — boilerplate every aggregator template carries — while
the 78 programme links that make it an index never disqualify it.

--------------------------------------------------------------------
BYPASS #1 — marketing page extracted via UNKNOWN
--------------------------------------------------------------------
URL:   https://www.prospects.ac.uk/postgraduate-recruiters
Result: classify_page_intent -> UNKNOWN / 0.0
Evidence:
  title      = 'Successful postgraduate recruitment starts with Prospects | Prospects.ac.uk'
  headings   = ['Successful postgraduate recruitment starts with Prospects',
                'Fill your postgrad courses and raise your profile',
                'Working with you to build a bespoke recruitment package',
                'Who do you want to reach?', 'Why work with Prospects?', ...]
  funding_mentions = 0
  programme_links  = 0

Why the existing page intent does not stop it: UNKNOWN is *deliberately*
extracted. `acquire_from_source` skips only pages whose intent is neither
DETAIL nor UNKNOWN, and the code comments the reason — "UNKNOWN means the
classifier did not find enough evidence either way, not that the page is known
to be a list — and discarding those would throw away real opportunities on a
signal that is silent rather than negative."

That reasoning is sound for a page that *might* be a scholarship. It is wrong
for a page with **zero** funding vocabulary anywhere, where UNKNOWN is not
"insufficient evidence" but "positive evidence of absence". The extractor then
picked the page's largest metric heading, "970,000 registrants", as the
scholarship name, and the quality gate — which checks name/provider/country/
URL — had nothing to object to.

--------------------------------------------------------------------
CALIBRATION CONSTRAINT (measured, not assumed)
--------------------------------------------------------------------
USTEP — https://www.u-tokyo.ac.jp/en/current-students/ustep-typeu.html —
is ALSO UNKNOWN/0.0 with funding_mentions=0 and programme_links=1, and it was
legitimately extracted and approved in V0.1.

Therefore a guard of the form "UNKNOWN and no funding claim => reject" is
UNSAFE. It would kill a real record. The guard must key on what distinguishes
prospects from USTEP, not on the shared UNKNOWN verdict:

  prospects  21 headings, all marketing segments, no award named anywhere,
             metric-shaped heading ("970,000 registrants"), 0 programme links
  USTEP       2 headings, one of which names a specific programme
             ("University-wide Student Exchange Program (USTEP) Type U")

--------------------------------------------------------------------
Best insertion point
--------------------------------------------------------------------
`services/exploration/acquisition_service.py`, inside
`acquire_from_source`, immediately after

    verdict, signals = self._page_intent(raw_doc)

and BEFORE the `run_pipeline(...)` call.

Rationale:
 * It is the single choke point every fetched page passes through, so one
   insertion covers both bypasses and any future caller.
 * It is strictly before extraction, so no Scholarship row is created and
   ReviewService.approve is never reached — the brief's Step 5 requirement.
 * It reuses the already-computed `verdict` and `signals`; no second fetch,
   no second classifier (Step 4).
 * The existing evidence channel is right there: `_record_signals(...)` writes
   `evidence.page_signals` on the frontier row, so the guard's verdict and
   evidence land in the existing audit trail with no new telemetry (Step 5).
 * It does not weaken the quality gate, which stays exactly as it is.

`scripts/v01_phase3_acquire.py` mirrors this loop and must be wired too, or it
would remain a bypass in the operational tooling.

--------------------------------------------------------------------
RESOLUTION NOTE (added after implementation)
--------------------------------------------------------------------
The insertion point above was "immediately after `_page_intent(raw_doc)`". The
implementation places the guard one step later — after the existing
`if verdict.intent not in (SCHOLARSHIP_DETAIL, UNKNOWN): continue` gate — which
is a deliberate refinement, not a deviation from the finding:

 * It avoids computing a listing verdict for a page that has already been
   refused for a stronger reason (an index or overview page), so the frontier
   records one verdict per page instead of two competing ones.
 * The reasoning that made this location safe is unchanged: the guard still
   runs before `run_pipeline(...)`, so no `Scholarship` row is created, and
   `_record_signals(...)` still carries the verdict into the existing
   evidence channel.

Both bypasses remain covered: the aggregator is `SCHOLARSHIP_DETAIL` and the
marketing page is `UNKNOWN`, so both pass the intent gate and reach the guard.
`tests/integration/test_acquisition_listing_guard.py` asserts this explicitly
(`pages_skipped_not_detail == 0` alongside `pages_skipped_listing == 1`), so
the suite fails if a fixture ever starts being stopped by intent instead —
which would mean the guard had stopped being the thing under test.

The operational script was wired too.
